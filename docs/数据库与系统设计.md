# 数据库与系统设计

设计基线：2026-10-22；第一阶段。依据原始要求及本次对话中的用户决策。所有持久化业务数据均存 MongoDB，浏览器只持有会话 Cookie 和当前未保存的输入。

## 1. 架构及边界

浏览器 Vue 3 → NestJS API → Mongoose → MongoDB 7 单节点副本集。生产构建由后端同源提供静态页面，开发环境由 Vite 代理 `/api`。单体结构适合课程项目，避免拆分服务增加部署成本。

后端分为 HTTP 层 `main.ts`、业务层 `service.ts`、领域规则 `domain.ts` 和数据库层 `database.ts`。规则引擎不依赖数据库，可独立测试。前端通过题型分支提供编辑、回答和统计组件，题型共同使用稳定数据契约。

第一阶段不包含游客填写、发布后改题、部分排序、矩阵逐行必答设置、新题型条件跳转或复杂条件分组。

## 2. 集合设计与关联

所有集合 `_id` 均为 ObjectId；业务关联 ID 使用其十六进制字符串。客户端不能自行指定创建者或填写者，后端从会话推导。

| 集合              | 主要字段与类型                                                                                                                                                                        | 作用                               |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| users             | username/string；usernameNormalized/string；passwordHash/string                                                                                                                       | 独立账号，密码采用随机盐 scrypt    |
| surveys           | ownerId/string；publicId/string；status/enum；draft/object；publishedVersionId/string?；deadlineAt/Date?；revision/number；submissionSerial/number；publishedAt/Date?；closedAt/Date? | 管理、草稿及当前接收状态           |
| survey_versions   | surveyId/string；versionNumber/number；schemaVersion/number；definition/object                                                                                                        | 不可变发布内容快照                 |
| response_attempts | surveyId/string；surveyVersionId/string；userId/string?；anonymous/bool；status/enum；state/object；responseId/string?；expiresAt/Date                                                | 保存填写进度和版本冲突控制         |
| responses         | surveyId/string；surveyVersionId/string；attemptId/string；anonymous/bool；respondentId/string?；answers/object；activePath/string[]；submittedAt/Date                                | 最终答卷，提交后不可编辑           |
| submission_claims | surveyId/string；userId/string                                                                                                                                                        | 账号级提交名额，只在禁止重复时建立 |
| sessions          | tokenHash/string；userId/string；purpose/login或receipt；expiresAt/Date                                                                                                               | 会话和短期提交收据                 |
| auth_throttles    | key/string；count/number；expiresAt/Date                                                                                                                                              | 登录尝试限流，不依赖内存或 Redis   |

每个集合由 Mongoose 自动维护 `createdAt`、`updatedAt`。Mongoose `minimize:false` 保留空答案对象，避免空对象被自动省略后违反数据库验证。

问卷状态为 draft / published / closed。已截止是由 published 加 deadlineAt 计算的显示状态，不需要定时任务改写文档。第一阶段不提供重新开放。

## 3. 定义与题目

Definition：title（1～120 字）、description（最多 5000 字）、allowAnonymous、allowRepeatSubmissions、questions、schemaVersion=1，以及独立的routingMode规则模式。缺标记或legacy-v1使用旧算法；新建/明确升级草稿采用exclusive-branches-v1。此标记进入发布快照，不改旧快照、历史答卷或旧填写过程；答案结构未变，schemaVersion不升级。

Question：id、type、title（1～500 字）、description（最多 2000 字）、required、options、rows、validation、jumpRules。

- ID 为 1～64 位字母、数字、短横线或下划线，拒绝原型相关保留名；题目 ID 全问卷唯一，选项 ID 在本题唯一。
- 一份问卷 1～100 题；选项题 2～30 个选项；矩阵 1～30 行；每题最多 30 条跳转规则。
- 数组顺序是展示顺序；跳转只引用 ID，调整顺序不会把规则错误指向另一题。
- 题目、选项、校验与规则总是一起读取，且有明确规模上限，因此嵌入定义文档。
- 答卷和填写过程随使用增长，单独存放，避免 16 MiB 文档限制和单文档写竞争。

### 各题型的答案契约

| type            | validation                                   | answers[questionId] 示例                                  |
| --------------- | -------------------------------------------- | --------------------------------------------------------- |
| single_choice   | 无专属字段                                   | `"option_a"`                                              |
| multiple_choice | minSelections? / maxSelections?              | `["option_a","option_b"]`                                 |
| text            | minLength? / maxLength? / format?            | `"我的建议"`                                              |
| number          | min? / max? / integerOnly?                   | `20`                                                      |
| matrix          | 使用 rows 和 options                         | `{"row_1":"option_a","row_2":"option_b"}`                 |
| ranking         | 完整排序                                     | `["option_b","option_a","option_c"]`                      |
| time            | mode=date/time/datetime；earliest? / latest? | `"2026-10-22"` / `"18:30"` / `"2026-10-22T10:30:00.000Z"` |
| slider          | min / max / step；lowLabel? / highLabel?     | `8`                                                       |
| color           | 不支持透明度                                 | `"#AABBCC"`                                               |

可选空值不会写入 answers。文本去除首尾空白后按 Unicode 码点统计长度；数字仅接受 JSON 数值，整数限制还要求安全整数。手机号用 text + phone_cn_mobile，保留标识符语义。可选多选允许整题不答，但一旦回答必须满足数量约束。

矩阵必答时每行必答，可选时允许部分行。完整排序要求所有选项恰好一次；默认顺序不直接算作回答。评分的默认滑块位置也不直接算作回答，须操作或确认。

日期和时刻按固定格式字符串保存，不进行 UTC 转换。日期时间的答案在当前 schemaVersion 中保存规范 UTC ISO 字符串，保持 Mixed 答案结构在存取与校验间一致；它表示真实时刻，界面固定按 Asia/Shanghai 转换展示。此处是对初步方案“使用 BSON Date”的实现调整，避免同一答案经过 JSON 往返改变类型。截止时间、提交时间等系统时间仍使用 BSON Date。

## 4. 跳转与循环

Rule：id、operator、value、target。target 为题目 ID 或 END。

| 题型 | 运算符                   | value                      |
| ---- | ------------------------ | -------------------------- |
| 单选 | eq                       | 选项 ID                    |
| 多选 | any / all / exact        | 非空且不重复的选项 ID 数组 |
| 数字 | eq / gt / gte / lt / lte | 有限数值                   |
| 数字 | between                  | 两个端点数组，闭区间       |

规则按配置顺序执行；首条命中后停止。legacy-v1未命中顺序进入数组下一题。exclusive-branches-v1根据完整配置收集所有非END目标为分支题，其余为通用题；开始进入第一道通用题，未命中仅寻找后面的第一道通用题，没有则END；命中则直接进入目标或END。分支题也遵循同一算法，连续分支不是自动题组。可选题不答不触发条件规则。其余五种新增题型与文本题没有条件规则，但可以作为跳转目标。

分类由配置而非当前回答决定，不提供“被指向仍可顺序进入”的例外。不增加独立显示条件配置。统一的createRoutingPlan给出分类、入口、默认后继、实际后继和结构可能后继，开始、推进、改答、候选可达性、结构校验与最终提交共同使用。新模式无通用题时保存/发布拒绝NO_ENTRY。详细升级与前端契约见《专属分支与模式升级说明》。

填写状态将“显示位置”和“有效路径末端”分开：currentQuestionId 是查看/填写游标，activePath 是已确定路径前缀，尚未完成时其末项是待确认题；ready 表示路径已确定到 END 且题目均已确认，独立于查看游标。因此 ready=true 时也可以正在查看 Q1。

新增 navigationMode（answer/review）、confirmedQuestionIds、pendingAnswers、pendingConfirmedQuestionIds。确认集合区分“可选题已明确跳过”和“新路径中从未回答”；不能仅凭 answers 是否存在判断完成。候选答案单独隔离，不属于有效答案，禁止写入最终答卷或参与统计。

主动返回 rewind 只修改游标、查看模式和 revision；保留答案、有效路径、ready、候选数据及推进次数。advance 校验用户确认的当前答案，将当前有效答案及隔离候选合并为计算输入，从固定模式的实际入口沿已确认且合法的答案重算路径：同路保留、失效清理、遇到未确认或非法答案则停下补答；对可能汇合的旧答案保存在候选区。候选是否仍有可能到达采用该模式的规则目标和默认后继作保守图搜索，最终以实际命中决定恢复或清除。候选不能令未命中的分支被顺序进入。确认不变、路径不变时可直接回到提交确认，不要求重填后续题。

条件跳转真正重复到本次重算前缀中的题目时，仍执行循环截断：保留目标题答案供修改，清除其后答案和候选，将目标题标为未确认。已存在于旧路径但位于当前题后面的目标题不是循环。例如 Q1 改答后跳到旧 Q4，应保留 Q4。重放保留答案时发现循环也适用同一规则，不自动无限推进。

每次成功确认答案只计一次推进，内部重算复用答案不重复计数；仅返回查看和校验失败不计数，任何返回均不能重置计数。新字段采用增量扩展，数据库验证对其设类型约束但不要求旧文档必须存在；读取时 normalizeAttemptState 推导旧记录的确认状态，后续修改再持久化，不改旧答卷和发布版本。旧语义已经删除的答案无法凭空恢复。

每次成功推进计一次，校验失败不计数。最多 200 次；第 200 次到 END 可提交，否则禁止第 201 次，保留内容供查看及返回修改，需新建填写才能继续。界面从 180 次起提醒。

发布校验拒绝无效目标、类型不匹配、非法条件。结构可达性检查将默认后继和规则目标组成图；它只验证可能的出口，不证明实际答案一定退出。当前默认后继始终向后，因此该检查较保守；真正的循环保护来自运行时上限。

最终提交不接受客户端完整答案对象，而是读取后端保存的 state。逐题重新校验有效答案，检查有效路径每条边与当前答案对应、首题正确、末端为 END、路径无重复、没有失效分支或候选答案、确认集合与有效路径一致。完整路径在查看模式下仍可提交后端原答案；尚未确认的本地修改不构成后端改答。权限、revision、事务、限次占位和幂等提交机制保持不变。

## 5. 索引与数据库约束

| 集合              | 索引                                                         | 原因                 |
| ----------------- | ------------------------------------------------------------ | -------------------- |
| users             | usernameNormalized 唯一                                      | 防大小写变体重复注册 |
| surveys           | publicId 唯一；ownerId + createdAt(-1)                       | 链接唯一与本人列表   |
| survey_versions   | surveyId + versionNumber 唯一                                | 版本唯一             |
| response_attempts | expiresAt TTL；userId + surveyId + status                    | 7 天清理和恢复填写   |
| responses         | attemptId 唯一；surveyId + surveyVersionId + submittedAt(-1) | 幂等及统计查询       |
| submission_claims | surveyId + userId 唯一                                       | 并发限制每人一份     |
| sessions          | tokenHash 唯一；expiresAt TTL                                | 身份验证和会话清理   |
| auth_throttles    | key 唯一；expiresAt TTL                                      | 数据库持久化限流     |

启动时建立索引并通过 collMod 设置 strict/error 集合 JSON Schema 验证，约束必填字段、类型和枚举；领域层负责动态题型、跨字段和跳转引用校验。TTL 删除不是即时的，读取时仍检查 expiresAt。

数据库验证结构和索引的可执行来源为 `apps/api/src/database.ts`，不另维护一份易失真的 schema 副本。

## 6. 事务、竞争与幂等

发布事务：读取草稿与 revision → 校验 → 写发布版本 → 将问卷改为 published。失败全部回滚。

提交事务：确认填写归属、版本与结束状态 → 检查问卷接收状态 → 更新问卷 submissionSerial → 可选写提交占位 → 写答卷 → 标记填写完成并清理匿名身份 → 写短期提交收据。

提交也写问卷文档，使其与关闭/截止时间修改发生写冲突，由 MongoDB 事务重试按顺序处理。这样比先查状态再独立写答卷更可靠；代价是同问卷提交会竞争同一计数文档，适合本项目规模，后续大规模应用需重新评估。

answers 和路径整体用 state.revision 做乐观锁，避免同一填写在两个标签页相互覆盖。问卷草稿也用 revision。重复提交利用 attemptId 唯一索引与完成状态返回同一答卷；不同填写争抢同一账号名额由占位唯一索引保证，失败事务不残留占位或答卷。

## 7. 匿名和权限

必须登录。允许匿名由填写者选择，禁止匿名时记录账号 ID。匿名答卷不存 respondentId，提交后过程记录移除 userId。限次占位不存答卷 ID，创建者的任何接口都不能读取会话、占位或填写过程。

为匿名提交网络重试提供 7 天内短期收据：sessions 中保存 `SHA256(receipt:attemptId:userId)` 及 userId，不把用户 ID 放回匿名答卷。sessions.purpose 区分 login 与 receipt，身份验证只接受 login；提交收据不能当作登录令牌使用。管理员仍可通过后台记录和时间等关联信息，因此是对问卷创建者的业务匿名，不是系统不可追踪匿名。未提交过程需要身份用于恢复，7 天过期。

会话随机令牌只在 HttpOnly / SameSite=Lax Cookie 中，数据库存 SHA256；密码存随机盐 scrypt。写请求检查 Origin 主机名，同源代理访问；接口逐次检查归属。API 不执行定义内的任意代码。

## 8. 统计与演化

只读取 responses，通过 MongoDB 聚合 `$match`、`$project`、`$unwind`、`$group` 等计算，不保存易失真的冗余计数。多选百分比分母为本题回答数，可超过 100%。矩阵按行和列计数；排序统计平均名次、首选次数和名次分布；数字/评分平均值只包含实际回答；无数据返回 null。文本内容分页每页 20 条。

后续保留核心集合和接口语义。增加题型时扩展联合类型、校验、填写和统计组件；发布后修改可新增版本，旧答卷继续引用旧版本；改变答案结构时增加 schemaVersion 并提供迁移/兼容读取，不能覆盖旧发布快照。对旧功能持续运行本阶段测试。

MongoDB 适合有限规模的嵌套问卷定义、异构答案和规则。关系数据库也能实现，但会把题目、选项与不同校验规则拆成很多关联表；本设计采用聚合根而非机械模拟关系表，同时将独立增长数据分集合。
